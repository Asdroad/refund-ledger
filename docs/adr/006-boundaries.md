# 006. Границы сервиса

**Решение.** Леджер и выплаты — один контекст с одной БД, но два процесса: `Api` (gRPC) и `Worker` (фон).

**Почему.** Выплата и её проводка обязаны меняться атомарно. Разнести их по базам — значит заменить транзакцию сагой без всякой выгоды. Процессы разделены ради независимого масштабирования и чтобы сбой фона не ронял API.

**Слои.** Зависимости направлены внутрь: `Domain` ← `Application` ← `Infrastructure` ← `Api`/`Worker`. Это проверяет `ArchitectureTests`.

**Redis.** Кэшируются только оплаченные возвраты: они больше не меняются, значит, и сбрасывать кэш не нужно. При отказе Redis читаем из БД.

**За рамками.** Аутентификация (ожидается mTLS в сетке), лимит возврата по сумме заказа (им владеет сервис заказов), многовалютные проводки.
